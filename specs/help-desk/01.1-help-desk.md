## 1. Objetivo

Modal sobre a página [Tickets (01)](01-help-desk.md) para **abrir um chamado manualmente**.

Abre ao clicar em **+ Novo ticket**. O formulário é **dinâmico**: campos e seções mudam conforme o valor de **Tipo** (e, em alguns casos, **Serviço** ou **Grupo de serviço**).

Campos comuns na maioria dos tipos: centro de custo, **grupo de serviço** (com campos condicionais), prioridade, solicitante, descrição, anexos.

Inclui painel **Critérios de prioridade** (colapsável) nos tipos que o exibem; a prioridade selecionada aparece **destacada em verde claro** quando expandido. Outros tipos usam **legenda compacta** abaixo do select Prioridade.

Disponível para **solicitante** e **profissional help desk** (`gestec_help_desk:new`).

## 4. Campos do formulário

### 4.1 Formulário dinâmico por **Tipo**

O select **Tipo** é o **gatilho principal** das variantes de layout. O select **Grupo de serviço** aciona campos adicionais em alguns casos (§4.6).

Ao alterar **Tipo** ou **Grupo de serviço**:

1. Montar/desmontar campos condicionais (sem fechar o modal).
2. Limpar valores dos campos que deixam de existir.
3. Revalidar com schema Zod (`superRefine` ou union por tipo + regras por grupo).

| Tipo selecionado | Campos / seções extras | Oculta / altera |
|------------------|------------------------|-----------------|
| **Solicitação** | Layout padrão (§4.2) | — |
| **Melhoria** | Checkbox de ciência (§4.3) + painel Critérios | — |
| **Cancelamento de solicitações** | Tabela de cancelamentos (§4.4) | **Grupo de serviço**; inclui **Aplicativo / Processo** |
| **Interrupção de serviço** | Serviço + Tempo indisponibilidade (§4.5) | Subcampos por **Serviço** |
| **Incidente** | Layout padrão (igual Solicitação) — **TBD** confirmar com negócio |

| Grupo de serviço | Campos extras (independente do Tipo*) |
|------------------|---------------------------------------|
| **Aquisição / alocação** | Código do bem/equipamento (§4.6) | |

\*Exceto quando **Grupo de serviço** estiver oculto (ex.: Cancelamento).

**Implementação:** `form.watch("type")` + `form.watch("serviceGroupId")` + subformulários por variante.

## 5. Critérios de prioridade (colapsável)

Exibido nos tipos **Melhoria**, **Cancelamento** e layout inicial genérico. Nos tipos **Solicitação**, **Interrupção de serviço** (e demais com legenda compacta), o Figma usa apenas a **legenda compacta** sob Prioridade (§4.2).

### 5.1 Comportamento

| Estado | UI |
|--------|-----|
| Recolhido (default) | Caixa com borda; ícone ℹ + **Critérios de prioridade** + **Exibir** + chevron ▼ |
| Expandido | Texto do toggle → **Recolher** (ou manter **Exibir** com chevron ▲); lista cards P1–P4 |

Ao **alterar** o select Prioridade com painel expandido, o card correspondente atualiza destaque **em tempo real**.

### 5.2 Destaque da prioridade selecionada

Card da prioridade escolhida no formulário:

- Fundo **verde claro** (ex.: `bg-green-50` / token tema)
- Borda verde sutil (conforme Figma)

Demais cards: fundo branco, borda cinza.

### 5.3 Conteúdo dos cards (Figma)

| Prioridade | Título | Descrição | Prazo contato inicial |
|------------|--------|-----------|------------------------|
| **P1** | P1 (alta prioridade) | Situações de emergência que interrompem completamente o trabalho do usuário ou afetam operações essenciais da empresa, exigindo resposta imediata. | **Imediato** |
| **P2** | P2 (prioridade média) | Problemas com impacto significativo no trabalho do usuário ou em operações críticas que precisam ser resolvidos em algumas horas. | **4 a 8 horas úteis** |
| **P3** | P3 (prioridade normal) | Questões que afetam o trabalho do usuário, mas podem esperar por solução dentro de prazo razoável, sem causar interrupções graves. | **1 a 3 dias** |
| **P4** | P4 (prioridade baixa) | Problemas que não afetam diretamente o trabalho do usuário e podem ser resolvidos em prazo mais flexível, sem causar impacto significativo. | **3 a 5 dias** |

Textos fixos no frontend (constante ou i18n); alimentam SLA inicial do ticket no backend.

| Ação | Gatilho | Resultado |
|------|---------|-----------|

## 7. Validação (Zod)

Schema **discriminado por `type`** — exemplo simplificado:

```ts
const baseFields = {
  costCenterId: z.string().min(1),
  priority: z.enum(["p1", "p2", "p3", "p4"]),
  requester: z.string().min(2),
  description: z.string().min(10),
  attachments: z.array(z.instanceof(File)).optional(),
};

const newTicketSchema = z.discriminatedUnion("type", [
  z.object({
    type: z.literal("melhoria"),
    ...baseFields,
    serviceGroupId: z.string().min(1),
    improvementAcknowledged: z.literal(true),
  }),
  z.object({
    type: z.literal("cancelamento"),
    ...baseFields,
    applicationProcess: z.string().min(1),
    cancellations: z.array(z.object({
      requestNumber: z.string().min(1),
      justification: z.string().min(1),
    })).min(1),
  }),
  z.object({
    type: z.literal("interrupcao_servico"),
    ...baseFields,
    serviceGroupId: z.string().min(1),
    service: z.enum(["sistema", "infraestrutura"]),
    downtime: z.string().min(1),
    unavailableSystemId: z.string().optional(),
    unavailableInfrastructureId: z.string().optional(),
  }).superRefine(/* exige system OU infra conforme service */),
  z.object({
    type: z.literal("solicitacao"),
    ...baseFields,
    serviceGroupId: z.string().min(1),
    assetCode: z.string().optional(),
  }),
  // … demais tipos com serviceGroupId + assetCode opcional
]).superRefine((data, ctx) => {
  const needsAsset =
    data.serviceGroupId === "aquisicao_alocacao" &&
    data.type !== "cancelamento";
  if (needsAsset && !data.assetCode?.trim()) {
    ctx.addIssue({ code: "custom", path: ["assetCode"], message: "Informe o código do bem/equipamento." });
  }
});
```

Erros inline via `FormMessage`; botão **Criar ticket** com loading durante submit.

## 8. Integrações / API

| Operação | Método | Endpoint | Quando |
|----------|--------|----------|--------|
| Criar ticket | POST | `/api/v1/gestec-help-desk/tickets` | Submit |
| Centros de custo | GET | `/api/v1/gestec-help-desk/cost-centers` | Abrir modal |
| Grupos de serviço | GET | `/api/v1/gestec-help-desk/service-groups` | Abrir modal |
| Serviços (interrupção) | GET | `/api/v1/gestec-help-desk/services` | Select Serviço |
| Sistemas | GET | `/api/v1/gestec-help-desk/systems` | Sistema indisponível |
| Infraestruturas | GET | `/api/v1/gestec-help-desk/infrastructures` | Infraestrutura inoperante |
| Upload anexo | POST | `/api/v1/gestec-help-desk/attachments` | Antes/depois do ticket — **TBD** |

**Payload variável por tipo** — exemplos:

```json
// Cancelamento
{
  "type": "cancelamento",
  "applicationProcess": "SAP",
  "cancellations": [
    { "requestNumber": "370331", "justification": "Duplicidade" }
  ]
}

// Interrupção — Sistema
{
  "type": "interrupcao_servico",
  "service": "sistema",
  "downtime": "2h",
  "unavailableSystemId": "uuid"
}

// Grupo Aquisição / alocação (qualquer tipo com grupo visível)
{
  "type": "solicitacao",
  "serviceGroupId": "aquisicao_alocacao",
  "assetCode": "PAT-12345"
}
```

**Response:** `201` + ticket criado (`id`, `status`, …)

**Permissão API:** `requireApiPermission(request, "gestec_help_desk", "new")`

**Regra backend:** se solicitante (sem `:view`), forçar `requesterUserId = session.userId`.

## 9. Regras de negócio

1. Modal **não** altera rota — overlay sobre `/gestec_help_desk`.
2. Profissional pode abrir chamado **em nome de** outro solicitante (campo texto + vínculo userId se selecionável — **TBD**).
3. Solicitante cria ticket sempre associado à **própria conta**.
4. Prioridade escolhida define SLA inicial (prazos dos critérios).
5. Anexos são opcionais.
6. Um modal aberto por vez.
7. Campos condicionais **não** persistem ao trocar Tipo (reset).
8. **Melhoria:** submit bloqueado sem checkbox de ciência.
9. **Cancelamento:** ao menos uma linha válida na tabela.
10. **Interrupção:** subcampo Sistema/Infraestrutura obrigatório conforme Serviço escolhido.
11. **Grupo Aquisição / alocação:** exige **Código do bem/equipamento** (independente do Tipo).
